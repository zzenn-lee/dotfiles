# /search 스킬 설계

작성 2026-11-24 · 대상 저장소 `zzenn-lee/dotfiles` · 상태: 승인 (2026-11-24)

## 1. 왜 만드나

여행·쇼핑·결혼 준비 같은 일상 검색을 할 때, 이미 설치한 검색 도구들을 한 번에 써서 **광고·협찬을 가려낸 판단 재료**를 모아 리포트로 받고 싶다. 지금까지 만족했던 결과물은 모두 아티팩트(웹 페이지)였다.

- 디즈니 크루즈 → 날짜별 일정표 + 팁 정리
- 옷·신발 → 상품별 링크 + 장단점, 브랜드 비교
- 결혼식 → 후기 모음

공통점: **하나를 골라 주는 답이 아니라, 정리된 재료를 보고 사용자가 판단**한다. 정리 틀은 주제마다 다르다.

## 2. 목표 / 목표 아님 / 실패로 보는 것

**목표**
- 요청을 보고 주제에 맞는 정리 틀을 제안하고, 확인을 받은 뒤 검색한다.
- 네이버·구글·쓰레드·Reddit·YouTube·지도·숙소를 필요한 만큼 섞어 쓴다.
- 협찬글을 **지우지 않고** 표시한다. 글마다 협찬 여부, 강조한 장점, 언급한 단점을 보인다.
- 항목마다 출처 링크·날짜·출처 등급을 붙이고, 소스끼리 엇갈린 점과 확인 못 한 것을 따로 적는다.
- 결과를 아티팩트로 만들고 같은 내용을 md 로도 남긴다.

**목표 아님**
- 하나를 골라 주는 추천, 예약·구매 대행
- 유료 도구(Apify 등), 로그인이 필요한 글(회원 전용 카페 글) 읽기
- 가격 알림 같은 주기 실행

**실패로 보는 것 (돌아가도 실패)**
- 협찬글을 말없이 빼거나, 협찬글 내용을 실사용 후기처럼 섞는 것
- 지어낸 링크·수치, 출처 없는 주장
- 1년 넘은 가격·영업시간·규정을 현재 정보처럼 쓰는 것
- 확인 없이 무료 한도(SerpAPI 월 250회, ScrapeCreators 한 번 받은 크레딧)를 크게 쓰는 것

## 3. 제약

| 도구 | 쓰는 곳 | 한도 |

| naver-blog MCP | 블로그 본문 전체 | 제한 없음 |
| serpapi MCP | 구글 웹·쇼핑·호텔·항공·지도, `site:` 검색 | **월 250회** |

| **WebSearch** (Claude Code 기본) | **일반 웹 검색의 기본** — 영어·해외 정보, 공식 사이트 찾기, `site:` 없는 넓은 검색 | 무료(한도 걱정 없음). 결과가 미국 기준이라 한국 지역 결과는 약함 |

- 협찬 표시는 블로그 글 **맨 아래**나 이미지 배너로 붙는 일이 많아, 검색 API 미리보기로는 못 잡는다.
- 새 MCP 는 새 Claude Code 세션에서만 보인다.

## 4. 만드는 방법 (Approaches)

| | 내용 | 판단 |
|---|---|---|
| ① 지시문만 | `SKILL.md` 한 장. Claude 가 블로그 본문을 하나씩 읽고 협찬 판단 | 글이 20~30개만 넘어도 느리고 판단이 흔들림 |
| **② 지시문 + 협찬 판별 스크립트** | ①에 Python 스크립트 하나: 블로그 URL 목록 → 본문을 받아 협찬 신호를 규칙으로 찾고, 판단 근거와 본문 발췌를 돌려줌 | **선택.** 협찬 판별은 매번 같은 기준으로 빠르게, 정리·판단은 Claude 가 |
| ③ 전용 MCP 서버 | 모든 소스를 감싸는 새 MCP | 이미 설치한 MCP 와 겹침. 품에 비해 얻는 게 적음 |

사용자가 ②를 골랐다(2026-11-24).

## 5. 사용자가 정한 것

1. **검색 전에 틀을 한 번 확인받는다.** 스킬은 먼저 계획(정리 틀 · 볼 곳 · 예상 사용 횟수)을 보여 주고 "ㄱ"/수정을 기다린다.
2. **결과는 정리본 리포트**, 판단은 사용자. 틀은 주제에 맞춰 스킬이 제안한다.
3. **협찬글은 표시만 하고 남긴다.** 글마다 강조한 장점·언급한 단점을 보이고, 협찬글이 강조한 점과 실사용 후기 평가를 비교한다.
4. Instagram 은 쓰지 않는다(영상 위주). Threads 는 쓴다.
5. 유료 도구는 쓰지 않는다.
6. **이 Mac 의 Claude Code 에서만 쓴다** (SSH·원격 포함). 계획 확인은 대화로, 결과는 claude.ai 아티팩트 링크로.
7. **일반 검색은 WebSearch 를 먼저 많이 쓴다.** SerpAPI 는 WebSearch 로 안 되는 것에만: 한국어·한국 지역 구글 결과, 구글 쇼핑·호텔·항공권·지도, `site:` 로 특정 한국 커뮤니티 찾기.

## 6. 동작 흐름

```
/search <요청>
  │
  ▼
① 계획 제안  ── 주제 판단 → 정리 틀, 볼 곳, 예상 사용(구글 N회, 쓰레드 N회)
  │             "이대로 할까요?" → 사용자 확인 (수정이면 계획만 다시)
  ▼
② 모으기     ── 계획한 소스별 검색 (WebSearch → 네이버 → 필요할 때만 SerpAPI → last30days → 지도·숙소)
  │
  ▼
③ 협찬 판별  ── 네이버 블로그 URL 들 → sponsor_check.py → 협찬 여부·근거·본문 발췌
  │
  ▼
④ 읽고 뽑기  ── 글마다 강조한 장점 ≤3, 언급한 단점 ≤3 (없으면 "언급 없음")
  │             출처 등급, 날짜, 반응 수
  ▼
⑤ 교차 확인  ── 같은 주장이 서로 다른 출처 2곳 이상이면 "확인됨", 1곳이면 "한 곳만"
  │
  ▼
⑥ 리포트     ── 아티팩트 게시 + md 저장 → 링크와 3줄 요약을 답장
```

## 7. 리포트 모양

틀은 주제마다 다르지만 **뼈대는 같다.**

```
0. 요약        무엇을 찾았나 · 본 출처 수(등급별) · 협찬 의심 비율 · 기준 날짜
1. 본문        ← 주제별 틀 (예: 날짜별 일정표 / 상품 비교 표 / 업체별 후기 모음)
               항목마다: 내용 · 출처 링크 · 날짜 · 등급 배지 · (해당 시) 협찬 배지
2. 협찬 vs 실사용  협찬글이 공통으로 강조한 점 ↔ 실사용 후기의 평가 / 협찬글인데도 나온 단점
3. 엇갈린 점·확인 못 한 것   소스끼리 다른 말, 한 곳만 나온 주장, 오래된 정보
4. 출처 목록   전체 링크 표 (등급 · 날짜 · 협찬 여부)
```

**출처 등급**

| 등급 | 뜻 | 예 |
|---|---|---|
| A 공식 | 운영사·제조사·공공 | 디즈니 공식 Q&A, 브랜드 사이즈표 |
| B 실사용 | 직접 써 본 독립 후기 | Reddit 글, 카페 후기, 무신사 한달 후기 |
| C 정리글 | 모아 쓴 글, SEO 목록 | "성수 카페 BEST 10" |
| D 협찬·광고 | 협찬 표시가 있거나 강하게 의심 | 원고료·체험단 표시 블로그 |

**틀 예시** (스킬이 제안할 때 참고)

| 요청 성격 | 본문 틀 |
|---|---|
| 일정·여행 | 날짜(또는 장소)별 표 + 주제별 팁 + 예약 시기·주의 |
| 상품 고르기 | 상품 비교 표(링크·가격·장점·단점·사이즈/핏) + 브랜드별 특징 |
| 업체·서비스 후기 | 업체별 후기 카드(좋았던 점·아쉬운 점·가격대) + 공통 불만 |
| 그 밖 | 질문을 하위 질문 3~5개로 나눠 질문별 정리 |

## 8. 협찬 판별 스크립트 (`sponsor_check.py`)

- **입력:** 네이버 블로그 URL 목록 (JSON 또는 줄 단위)
- **하는 일:** `m.blog.naver.com/PostView.naver?blogId=…&logNo=…` 로 본문을 받아(기존 naver-blog MCP 와 같은 방식, 로그인 불필요) 신호를 찾는다.
  - 문구: 소정의 원고료, 제공받아, 지원받아, 협찬, 체험단, 광고, 유료 광고, 업체로부터, 내돈내산(협찬 표시와 같이 나오면 오히려 의심)
  - 링크·이미지: 체험단 사이트로 가는 링크나 이미지 주소 (레뷰·리뷰노트 등 — 목록은 스크립트 안 상수)
  - 위치: 맨 위 / 맨 아래 / 본문 중간
  - 업체 연락처·쿠폰 코드 반복
- **출력 (URL 마다):** `{url, title, date, verdict: 협찬|의심|없음|읽기실패, evidence: [문구와 위치], excerpt}`
- `excerpt` (빌더 판단): 장단점이 끝부분에 몰리는 경우가 많아 **앞 600자 + 끝 600자 + 장단점 단어(장점·단점·아쉬운·별로·불편·비추·좋았·만족·재방문 등) 주변 문단**을 합쳐 약 3,000자까지 준다. ④는 이 발췌만 읽는다 — 본문 전체를 다시 읽지 않는다.
- 이미지 안 글자는 못 읽는다 → 배너가 이미지뿐이면 "없음"으로 나올 수 있음. 리포트에 이 한계를 적는다.
- 테스트 (빌더 판단): dotfiles 는 **공개 저장소**라 남의 블로그 원문을 올리지 않는다. 실제 글 구조를 본뜬 **직접 만든 표본 HTML**(협찬 문구 위/아래, 체험단 배너 링크, 일반 글, 내돈내산+협찬 혼합)로 네트워크 없이 판정을 확인한다. 실제 글로 해 본 확인은 git 밖에서만 한다.

## 8-1. 네이버 카페 글 (빌더 판단)

- 검색 API 가 주는 제목·앞 100자와 SerpAPI 미리보기만 쓴다. 회원 전용 글은 읽지 않는다.
- 공개 글이라도 본문은 읽지 않고, 협찬 판별도 하지 않는다 → 리포트에 "카페 글은 미리보기만 봄"을 적고 링크를 남겨 사용자가 직접 열어 보게 한다.
- 결혼 준비처럼 카페가 주 소스인 주제에서는 이 한계가 크다. 계획 단계에서 미리 알린다.

## 8-2. last30days 쓰는 법 (빌더 판단)

- 이름과 달리 `--days` 로 기간을 바꿀 수 있다. 지금 이야기(유행, 최근 후기)는 기본 30일, 오래 가는 정보(크루즈 팁, 제품 후기, 업체 평판)는 `--days 365`.
- 결과를 다른 소스와 합치기 위해 `--emit=json` 으로 받는다 (last30days 자체 리포트 형식은 쓰지 않음).
- 1년보다 오래된 Reddit·YouTube 글이 필요하면 SerpAPI `site:reddit.com` 등으로 보충한다.

## 9. 사용 한도 기본값

| 도구 | 한 번 검색에 쓰는 기본 상한 | 넘길 때 |
|---|---|---|
| SerpAPI | 10회 | 계획에 적고 확인 받기 |
| last30days (ScrapeCreators 크레딧) | **크레딧 100** (실행 전후 잔액을 조회해 실제 사용량을 리포트에 적음) | 계획에 적고 확인 받기 |
| 블로그 본문 판별 | 30개 | 넘으면 반응·최신 순으로 자르기 |

계획 단계에서 SerpAPI 남은 횟수와 ScrapeCreators 남은 크레딧을 보여 준다.

## 10. 파일 위치

```
dotfiles/search/skills/search/
├─ SKILL.md
└─ scripts/sponsor_check.py (+ tests/, 표본 HTML)
```
- `install-mac.sh` 가 `~/.claude/skills/search` → 위 폴더로 링크를 만든다.
- 리포트 md 저장: `~/Documents/search-reports/YYYY-MM-DD-<주제>.md` (빌더 판단 — 사용자가 바꿀 수 있음)

## 11. 빌더에게 맡기는 것

- SKILL.md 문장, 틀 제안 문구, 아티팩트 디자인 세부
- 협찬 문구·체험단 도메인 목록의 정확한 내용(표본으로 조정)
- 검색어 만드는 요령(한국어/영어 병행, `site:` 대상 고르기)
